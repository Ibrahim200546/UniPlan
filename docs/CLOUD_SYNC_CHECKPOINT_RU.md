# Облачное сохранение 1.2.0

Room — локальное хранилище, Supabase — копия учебных записей аккаунта. Синхронизация запускается явно в профиле. До успешного ответа локальные изменения остаются отмеченными как несохранённые в облаке. Без интернета CRUD работает локально. Автоматической фоновой синхронизации в этой версии нет.

Таблица public.uniplan_state хранит одну строку на UUID пользователя: revision, payload, updated_at. RLS разрешает пользователю читать и изменять только свою строку; anon не получает доступа. RPC save_uniplan_state(expected_revision,data) использует auth.uid() и SECURITY INVOKER, а не UID из клиентского JSON. Первое сохранение ожидает revision 0, следующие — известную клиенту версию. Конкурентный устаревший запрос возвращает конфликт.

Payload версии 1 включает профиль, предметы, задания, занятия и заметки. Пароли, токены, пути файлов и настройки устройства в него не входят. Клиент проверяет типы, размеры, уникальность ID, ссылки на предметы и допустимые URL до импорта. Ограничение клиента — 1,5 МБ и 10 000 записей; сервер ограничивает JSON двумя МиБ. При превышении данные остаются локально, синхронизация сообщает об ошибке.

Импорт выполняется целиком в транзакции: локальные ID заново выдаёт Room, ссылки переназначаются. Удаляются/заменяются только записи текущего владельца. Другой аккаунт и его экспортированные файлы не затрагиваются.

Room мигрирует 1 → 2 → 3 без destructive migration. Версия 3 добавляет sync_state с облачной ревизией и признаком локальных изменений; прежние профили считаются несинхронизированными. Запись учебных данных и признак изменения фиксируются в одной транзакции.

Сетевые операции и локальные записи упорядочены одним executor. Сессия повторно проверяется после сети и перед импортом. Выход во время запроса запрещает применять ответ к следующему аккаунту. Задержка сети может задержать сохранение формы до сетевого таймаута.

Если обе копии изменены, ни одна не заменяется автоматически. Пользователь выбирает локальную или облачную версию, затем подтверждает замену. Выбор привязан к показанной облачной ревизии и точному локальному снимку: новые изменения требуют нового выбора. Неопределённый результат запроса после обрыва сети также может потребовать разрешения конфликта.

Локальные тесты покрывают перенос между двумя базами, смену сессии, повреждённый JSON, конфликт версий и гонку сохранений. Состояние реального сервера и email-сценариев см. в [отчёте](TEST_REPORT.md); настройка — в [SUPABASE_SETUP_RU.md](SUPABASE_SETUP_RU.md).
