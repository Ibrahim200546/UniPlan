# Архитектура UniPlan 1.1.0

Автор учебной работы: **Тәңірберген Ибраһим**, группа **АЖҚ-321**, специальность «Ақпараттық жүйелер».

UniPlan — нативный органайзер на Java с XML-интерфейсами. Общий модуль `app` содержит пользовательские сценарии, Room и файловое хранилище. Варианты `demo` и `firebase` подключают разные реализации интерфейса авторизации; локальные функции общие.

## Поток данных

```text
Activity / Fragment / Adapter
             │ действие пользователя
             ▼
          ViewModel
             │ вызов repository; состояние формы в SavedStateHandle
             ▼
       StudyRepository                 NoteFiles
             │ ExecutorService            │ ExecutorService
             ▼                            ▼
       StudyDao → Room              UTF-8 / AtomicFile / SAF
             │ LiveData                   │ callback в главный поток
             └────────────────────────────┘
```

Activity и Fragment отображают данные и обрабатывают события. ViewModel хранит состояние экрана и вызывает repository. `StudyRepository` проверяет значения, получает действующего владельца из `AuthRepository`, выполняет операции с Room в отдельном потоке и возвращает результат в главный поток. `NoteFiles` отвечает только за явные текстовые копии и экспорт. UI не обращается к DAO напрямую.

Сохранённые записи находятся в Room. Незавершённая форма хранится отдельно в состоянии ViewModel; она не становится сохранённой записью до действия «Сохранить». Компоненты не рассчитывают на гарантированный вызов `onDestroy()`.

При появлении действующей сессии repository создаёт локальный профиль через `INSERT IGNORE`, даже если экран профиля ещё не открыт. Для первого демопрофиля перед этим выполняется однократный импорт персонального расписания: он устанавливает Ибраһим / АЖҚ-321 при первом применении набора. После этого повторный вход не перезаписывает изменённые пользователем имя и группу.

## Схема базы данных

| Таблица | Ключ и существенные поля | Связи |
|---|---|---|
| `profiles` | `ownerUid` — первичный ключ; имя, учебная группа | Один локальный профиль на UID |
| `subjects` | `id` — автоинкремент; `ownerUid`, название, преподаватель, цвет, значок | Родитель для учебных записей |
| `tasks` | `id`, `ownerUid`, `subjectId`, название, описание, тип, срок, приоритет, выполнено, даты создания/изменения | Обязательный предмет того же владельца |
| `lessons` | `id`, `ownerUid`, `subjectId`, день недели, начало, конец, аудитория; `lessonNumber`, `lessonType`, `teacher`, `meetingUrl` | Обязательный предмет того же владельца; преподаватель занятия может отличаться от преподавателя предмета |
| `notes` | `id`, `ownerUid`, необязательный `subjectId`, заголовок, текст, даты | Предмет того же владельца либо `NULL` |
| `seed_state` | `ownerUid` — первичный ключ; `seededAt` | Фиксирует однократную явную загрузку примеров |
| `dataset_imports` | Составной первичный ключ `(ownerUid, datasetKey)`; `importedAt` | Фиксирует применение отдельного набора персонального расписания |

`id` уникален в пределах таблицы. Составной уникальный индекс `(ownerUid, id)` у предметов позволяет задать составной внешний ключ `(ownerUid, subjectId)` у заданий, занятий и заметок. SQLite отклоняет связь с предметом другого аккаунта даже при ошибке выше уровня DAO.

Индексы `(ownerUid, dueAt)`, `(ownerUid, dayOfWeek, startMinute)` и `(ownerUid, updatedAt)` поддерживают выборки владельца с сортировкой. Отдельные индексы внешних ключей нужны для проверки связей. Поиск и фильтры экранов работают по уже ограниченным текущим владельцем спискам.

Удаление связанного предмета использует `RESTRICT`: связанные записи остаются на месте. Repository проверяет связи и возвращает понятный код `linked`. Пользователь сначала изменяет предмет у записей или удаляет сами записи. Для необязательной связи заметки можно выбрать отсутствие предмета.

Срок задания хранится как Unix-время в миллисекундах и отображается в часовом поясе устройства. Просроченность не записывается в отдельную колонку: она вычисляется как `!completed && dueAt < now`. Недельное расписание использует дни 1–7 (понедельник–воскресенье) и минуты от начала дня. Допускаются занятия в пределах одного дня, с окончанием строго позже начала.

Номер пары и вид занятия описывают конкретную запись расписания. Поле `teacher` позволяет сохранить разных преподавателей лекций, практических и лабораторных занятий по одному предмету. Если оно пустое, экран использует преподавателя из предмета. `meetingUrl` хранит предоставленный URL; несмотря на историческое имя поля, это может быть обычная ссылка на страницу или адрес, а не видеовстреча. Непустой URL открывается внешним приложением только по действию пользователя. Проверка доступности внешнего сервиса или содержимого ссылки не является частью импорта.

## Как разделены пользователи

1. Источник личности — действующая сессия `AuthRepository`, а в основном варианте — Firebase Authentication. UID не берётся из Intent, формы или файла.
2. Списки, чтение по ID, изменение, удаление и проверка связей ограничены UID. Чтение чужого ID возвращает «запись недоступна» без раскрытия содержимого.
3. Вставка присваивает доверенный UID. Непустой входной `ownerUid`, не совпадающий с сессией, отклоняется.
4. Перед постановкой операции в очередь repository копирует входную entity и захватывает объект сессии. Фоновый код использует захваченный UID. Он не перечитывает новый UID для записи после смены аккаунта.
5. Если сессия изменилась, результат старой операции не передаётся как успешные данные новому экрану. Даже если начавшаяся транзакция завершилась после выхода, она относится только к старому владельцу.
6. `MediatorLiveData` снимает прежнюю подписку и сразу выдаёт пустой список или `null`, затем подключает запрос нового владельца. Это предотвращает краткое отображение значения, оставшегося от предыдущей подписки.
7. Основная Activity следит за авторизацией и закрывает доступ к внутренним экранам при выходе или смене владельца. Значения extras могут использоваться для приветствия, но не подтверждают личность.

Разделение UID — правило приложения и базы данных, а не шифрование файлов. Доступ к данным на взломанном устройстве или через отладочный доступ не входит в модель защиты учебного проекта. Пароли в Room, SharedPreferences, файлы и журнал не записываются.

## Транзакции и фоновые операции

Все изменения repository выполняются в `RoomDatabase.runInTransaction()`. Проверка существования/владельца и изменение происходят вместе. Для удаления задания транзакция возвращает снимок удалённой записи. Undo восстанавливает её исходный ID; повторное Undo не создаёт дубль и не перезаписывает более новую запись.

Примеры демонстрационного режима и отметка `seed_state` создаются одной транзакцией. Если операция прервётся с ошибкой, не останется половины набора. Повторное явное действие возвращает признак «уже загружено». Удаление всех примеров вручную не сбрасывает эту отметку.

### Персональный набор расписания

В версии 1.1.0 `PersonalSchedule.importOnce()` запускается автоматически при появлении сессии только при `auth.isDemo()` и UID `demo-1`. Ключ набора — `ibrahim_azhq321_timetable_v1`. В одной транзакции создаются недостающие предметы, добавляются занятия, обновляется начальное имя/группа профиля и записывается отметка `dataset_imports`.

Источник — расписание, переданное пользователем: **23 занятия по семи предметам**, распределение по дням с понедельника по субботу — **6 / 4 / 3 / 6 / 3 / 1**. Это локальная загрузка данных, а не запрос к университетскому порталу. Существующий предмет с точно совпадающим названием переиспользуется без изменения его преподавателя, цвета и значка. Полностью идентичная запись занятия пропускается; прежние отличающиеся занятия, задания, заметки и файлы не удаляются и не заменяются.

При первом импорте старый первый демопрофиль, ранее называвшийся Айдана, получает имя Ибраһим и группу АЖҚ-321. Это одноразовое изменение, привязанное к маркеру набора. Дальнейшие изменения имени, группы и расписания сохраняются. Повторный вход не восстанавливает удалённые пользователем занятия. Если в базе были другие уроки, общее число может превышать 23. Таблица `dataset_imports` независима от `seed_state`, поэтому явная загрузка учебных примеров остаётся отдельным действием.

В последней строке набора сохранён исходный адрес «Талдыкорган қ, Жансугуров көшксі 226» и адресный URL студенческого портала. Он трактуется как обычная внешняя ссылка. Доступность URL портала и ссылок Google Meet не проверена; никакие внешние сервисы этим импортом не настраиваются.

Запросы по ID, мутации и файловые операции выполняются через `ExecutorService`. Room сам исполняет наблюдаемые запросы вне UI-потока. `allowMainThreadQueries()` и destructive migration не используются. Ошибки возвращаются кодами `validation`, `missing`, `linked`, `session`, `io`, `unknown`; UI показывает локализованный текст, а не содержимое исключения.

## Три способа хранения из девятой лекции

| Механизм | Что хранит | Где искать в Device Explorer |
|---|---|---|
| SharedPreferences | Тема и язык, две палитры оформления устройства; отдельные предпочтения вида заметок для UID | `/data/data/<applicationId>/shared_prefs/` |
| Internal Storage | Явные копии текста заметок | `/data/data/<applicationId>/files/note_copies/<SHA-256 UID>/note_<ID>.txt` |
| App-specific External Storage | Явные копии текста заметок в собственной внешней папке | `/storage/emulated/0/Android/data/<applicationId>/files/note_copies/<SHA-256 UID>/note_<ID>.txt` |
| Room | Основные записи и связи | `/data/data/<applicationId>/databases/uniplan.db` и служебные WAL/SHM-файлы |
| Storage Access Framework | TXT в месте, которое выбрал пользователь | Зависит от выбранного системного провайдера документов |

Для demo `<applicationId>` равен `kz.uniplan.app.demo`, для основного варианта — `kz.uniplan.app`. Реальный корень внутренних данных Android может отображаться как `/data/user/0/`; это эквивалентный путь текущего пользователя устройства.

`getExternalFilesDir()` — собственная внешняя папка приложения, **не общедоступные «Загрузки»**. Это уточнение к упрощённой аналогии «общего почтового ящика» из лекции 9. Для пользовательского «Сохранить как…» применяется `CreateDocument` и `ContentResolver`, без широких разрешений на хранилище.

Копии доступны только после сохранения заметки с реальным ID. Перед чтением и записью `NoteFiles` проверяет принадлежность заметки. Имя файла строится из числового ID, каталог — из SHA-256 UID; заголовок не участвует в пути. UTF-8 задаётся явно, потоки закрываются. Внутренние и внешние копии записываются через `AtomicFile`, чтобы незавершённая запись не заменила целый предыдущий файл. Для внешнего каталога проверяются доступность и состояние носителя.

Открытие копии загружает текст в редактор по явному действию. Room остаётся без изменений, пока пользователь не сохранит форму. Отмена системного выбора файла возвращает результат отмены без сообщения об ошибке. «Сохранено» возможно только после успешного закрытия потока. Публичный экспорт связан с UID, захваченным экраном, и отклоняется при смене аккаунта.

## Пользовательское оформление

Экран **«Профиль → Оформление / Безендіру»** использует `AppearancePalette` с четырьмя значениями: цвет фона, цвет блоков, акцент и радиус скругления. Цвет задаётся пресетом либо HEX `#RRGGBB`; символ `#` необязателен, цвет непрозрачен. Радиус ограничен диапазоном **0–32 dp**. Предпросмотр показывает выбранный набор перед сохранением; неправильный HEX вызывает ошибку у поля и блокирует применение.

Переключатель светлой/тёмной палитры выбирает редактируемый набор, а не меняет глобальную тему. «Применить и сохранить» сохраняет его и обновляет активное оформление на месте, без пересоздания Activity. Экран остаётся открытым. Сброс требует подтверждения и сразу сохраняет значения по умолчанию только для выбранной палитры.

`SettingsStore` сохраняет данные в глобальном `device_settings`: ключи светлой палитры начинаются с `appearance_day_`, тёмной — с `appearance_night_`. Для каждой отдельно записываются `background`, `card`, `accent`, `corner`. Сохранение или сброс одной палитры не меняет другую. Эти параметры общие для аккаунтов внутри одного установленного flavor; вид заметок остаётся в отдельных аккаунтных настройках.

`Appearance` применяет текущую палитру к экрану и Material-компонентам. Цвет текста выбирается с учётом яркости поверхности; `AppearancePalette.legible()` при необходимости корректирует акцент для контраста. Пользовательский HEX остаётся исходным сохранённым цветом, но конкретная подпись или значок могут использовать его скорректированный вариант. Это не является заявлением о пройденной полной проверке доступности интерфейса.

У предмета отдельно сохраняются собственные цвет и значок в Room. Его HEX-цвет относится к конкретному предмету и владельцу, а не к глобальному фону приложения. Имя и учебная группа показываются на главной; дата форматируется для выбранного языка приложения. Изменение оформления не преобразует и не удаляет учебные записи.

## ООП и связь с лекциями

Вторая лекция рассмотрена полностью: классы и объекты, модификаторы доступа, инкапсуляция, наследование, перегрузка, переопределение, абстрактный класс и интерфейс. В UniPlan приватные неизменяемые поля `StudyItem` проходят валидацию конструктора. `AssignmentItem` и `ExamItem` переопределяют `type()` и `typeKey()`; фабрика `StudyItem.from()` возвращает абстрактный тип, который используется интерфейсом. Перегрузка `isOverdue()` / `isOverdue(now)` позволяет проверять одну и ту же логику с реальным и заданным временем. `AuthRepository` отделяет потребителя авторизации от Firebase и demo.

Пример Book/EBook из практики лекции не скопирован буквально: те же навыки применены к учебным заданиям. Room entities оставлены простыми классами, чтобы демонстрационное наследование не усложняло таблицы.

Девятая лекция также прочитана полностью. Реализованы SharedPreferences, отдельные внутренние/внешние файловые копии и их чтение. В отличие от сокращённых примеров лекции код явно использует UTF-8, читает поток до конца, проверяет ошибки и не считает пустую строку доказательством удачного чтения.

## Локальная работа, резервное копирование и развитие схемы

Firebase Authentication подтверждает аккаунт и поддерживает сессию. Он **не синхронизирует** учебные записи Room между устройствами. При сохранённой сессии локальные записи доступны без сети; новый вход, регистрация и восстановление пароля требуют соединения.

Android backup для учебных данных отключён настройками приложения. Это исключает обещание восстановления локальной базы по входу в Firebase. Удаление приложения или очистка его данных удаляет Room, настройки и собственные файлы; TXT, экспортированные пользователем через SAF, подчиняются правилам выбранного хранилища. Текстовый экспорт не является полным резервным архивом базы и не переносит расписание или связи.

Текущая схема имеет версию **2**. В `AppDatabase.MIGRATION_1_2` четыре новых поля добавляются к `lessons` через `ALTER TABLE`, а таблица `dataset_imports` создаётся отдельно. Для прежних занятий `lessonNumber` получает `0`, текстовые поля — пустую строку. Существующие ID, владельцы, предметы, время и аудитории остаются прежними. Переход зарегистрирован через `addMigrations(MIGRATION_1_2)`; destructive migration не используется.

Процессор Room экспортирует JSON схем в `app/schemas/`. Схема 1 сохраняется для проверки обновления до схемы 2. Миграция структуры и персональный импорт — разные операции: миграция применяется ко всей базе при обновлении, а набор из 23 занятий — только к авторизованному локальному `demo-1` и только один раз. Firebase-аккаунты и второй демопрофиль этот набор автоматически не получают.

Фактические выполненные проверки и ограничения среды указаны отдельно в `TEST_REPORT.md`; наличие тестового класса само по себе не означает успешного прогона.
